# 7.19 — Adaptación del Sistema de Roles y Permisos por Tipo de Negocio

## NEGOVA — Arquitectura Multi-Tenant y Extensibilidad Progresiva

**Versión:** 2.0  
**Estado:** ✅ Implementado y Verificado  
**Fase:** Fase 7 — Seguridad, Control de Acceso y Autorización  
**Vertical Inicial:** Restaurante de Comida Rápida (Gastronomía)  
**Preparado para:** Barberías, Servicios, Retail, Mercados y Futuros Verticales  

---

## 1. Resumen Ejecutivo

NEGOVA es una plataforma SaaS multi-tenant que evoluciona de manera progresiva incorporando sectores comerciales según las necesidades de los clientes. El primer caso de uso comercial implementado es el **restaurante de comida rápida**.

Este documento detalla la arquitectura que desacopla y especializa los **permisos y capacidades operativas del rol Auxiliar (y Dueño)** según el **tipo de negocio (`business_type`)** y los **módulos implementados y habilitados**, sin requerir reconstrucciones del motor de autorización al integrar nuevos verticales.

---

## 2. Principios Arquitectónicos Clave

1. **Catálogo Central Sincronizado (Single Source of Truth):**
   - El catálogo de permisos reside en un esquema unificado (`src/lib/auth/permissions.ts`).
   - Sincronizado entre el panel del Superadministrador y el espacio de trabajo del Dueño (`Workspace`).
   - Los códigos de permisos (`resource.action`) son únicos, estables y normalizados.

2. **Categorización de Módulos (Universal vs. Especializado):**
   - **Módulos Core / Universales:** Módulos que aplican a todos los tipos de negocio (p. ej., `ventas`, `productos`, `clientes`, `inventario`, `gastos`, `empleados`, `configuracion_negocio`, `reportes`).
   - **Módulos Verticales / Especializados:** Módulos que aplican exclusivamente a un grupo de tipos de negocio (p. ej., `pedidos` / comandas solo para gastronomía; `citas` / turnos en el futuro para barberías/servicios).

3. **Defensa en Profundidad (Validación en Servidor):**
   - No basta con ocultar permisos en la interfaz de usuario.
   - El backend (`hasPermission`, `verifyUserPermission`, `verifyWorkspaceAction`) valida activamente que el permiso solicitado pertenezca a un módulo compatible con el `business_type` del tenant.
   - Cualquier intento de invocar operaciones de un vertical incompatible (ej. crear comanda en una barbería) es rechazado en servidor.

4. **Principio de Mínimo Privilegio para el Auxiliar:**
   - El rol **Auxiliar / Ayudante** está diseñado para las operaciones diarias de caja, ventas, toma de pedidos y registro operativo.
   - Acciones críticas (eliminación de productos/clientes/gastos, anulación de ventas facturadas, ajustes de inventario por merma, modificación de datos fiscales del comercio y exportación financiera) están **estrictamente reservadas al Propietario (`owner`)**.

## 4. Estructura de Datos en TypeScript

### 4.1 Definición de Módulos y Permisos

```typescript
export type ModuleReadinessStatus = "implemented" | "under_construction" | "not_applicable";

export interface PermissionDefinition {
  code: string;
  name: string;
  description: string;
  isAssignableToAuxiliar?: boolean;
  minRoleLevel?: "owner" | "auxiliar";
}

export interface PermissionModuleGroup {
  moduleId: string;
  moduleName: string;
  description: string;
  scope: "platform" | "business";
  status?: ModuleReadinessStatus;
  compatibleBusinessTypes?: string[]; // Si es undefined o ['*'], aplica universalmente
  applicableCategories?: string[];    // ['gastronomicos'], ['servicios'], ['comercios']
  permissions: PermissionDefinition[];
}
```

### 4.2 Funciones de Dominio para Adaptación

```typescript
// Obtener solo los módulos aplicables a este vertical
getPermissionModulesForBusinessType(businessType: string, scope: "business"): PermissionModuleGroup[];

// Obtener códigos de permisos disponibles para un tipo de negocio
getAvailablePermissionsForBusinessType(businessType: string): string[];

// Validar si un permiso es compatible con el tipo de negocio
isPermissionCompatibleWithBusinessType(permissionCode: string, businessType: string): boolean;

// Obtener permisos por defecto adaptados al vertical
getDefaultPermissionsForRoleAndBusinessType(roleCode: string, businessType: string): string[];

// Obtener permisos que el Dueño puede asignar al Auxiliar
getAssignablePermissionsForAuxiliar(businessType: string): string[];
```

## 5. Validación en Servidor (Capa de Seguridad)

En `src/lib/auth/authorization.ts`:

```typescript
// 1. Obtener tipo de negocio en base de datos
const { data: business } = await dbClient
  .from("businesses")
  .select("id, status, business_type")
  .eq("id", context.businessId)
  .maybeSingle();

const businessType = business.business_type || "restaurant";

// 2. Validación Estricta de Compatibilidad de Vertical
if (!isPermissionCompatibleWithBusinessType(permissionCode, businessType)) {
  return false; // Denegado a nivel de servidor
}
```

## 6. Guía para Incorporar Nuevos Verticales en el Futuro

Para agregar un nuevo vertical (ej. Barbería con agenda de citas):

1. **Registrar el vertical en `src/lib/businesses/types.ts`:**
   Asegurar que `"barbershop"` pertenezca a la categoría `"servicios"`.

2. **Declarar el módulo en `ALL_PERMISSION_MODULES` (`src/lib/auth/permissions.ts`):**
   ```typescript
   {
     moduleId: "citas",
     moduleName: "Citas y Agenda de Servicios",
     description: "Gestión de citas, agenda y turnos de atención",
     scope: "business",
     status: "under_construction",
     compatibleBusinessTypes: ["barbershop", "spa", "technical_service"],
     applicableCategories: ["servicios"],
     permissions: [
       { code: "appointments.view", name: "Ver Citas", description: "Consultar agenda", isAssignableToAuxiliar: true },
       { code: "appointments.create", name: "Agendar Cita", description: "Crear citas", isAssignableToAuxiliar: true },
       { code: "appointments.update", name: "Reprogramar Cita", description: "Modificar citas", isAssignableToAuxiliar: true },
       { code: "appointments.cancel", name: "Cancelar Cita", description: "Anular citas", isAssignableToAuxiliar: false, minRoleLevel: "owner" },
     ]
   }
   ```

3. **Resultado Inmediato:**
   - Los restaurantes seguirán viendo sus 9 módulos gastronómicos sin ver `citas`.
   - Las barberías verán los módulos universales y el nuevo módulo `citas`, sin ver `pedidos`.
   - Los auxiliares de cada negocio recibirán automáticamente los permisos que correspondan a su vertical.
   - El motor de seguridad validará y protegerá las rutas sin modificaciones de código adicionales.
