## 1. Objetivo

Convertir el modelo lógico relacional de NEGOVA en una representación formal en **Database Markup Language (DBML)** para visualizar esquemas interactivos (dbdocs.io / dbdiagram.io) y servir de plantilla directa para la generación de scripts DDL en PostgreSQL/Supabase.

Este esquema representa fielmente las 15 tablas y 19 relaciones definidas en los documentos 4.1 a 4.5.

---

## 2. Definición del Esquema DBML

```dbml
// ==========================================
// PROYECTO: NEGOVA - MVP RESTAURANTE

Table businesses {
  id uuid [pk]
  name varchar [not null]
  slug varchar [unique, not null]
  description text
  logo_url text
  phone varchar
  address text
  status varchar [default: 'ACTIVE', not null]
  created_at timestamptz [default: `now()`, not null]

Table users {

Table business_users {

  business_id uuid [not null]

  status varchar [default: 'ACTIVE', not null]
  created_at timestamptz [default: `now()`, not null]
  updated_at timestamptz [default: `now()`, not null]

  indexes {

  }
}

Table roles {
  id uuid [pk]
  name varchar [unique, not null]
  description text
  created_at timestamptz [default: `now()`, not null]
  updated_at timestamptz [default: `now()`, not null]
}

Table permissions {
  id uuid [pk]
  name varchar [unique, not null]
  description text
  created_at timestamptz [default: `now()`, not null]
}

Table role_permissions {
  role_id uuid [not null]
  permission_id uuid [not null]

  indexes {
    (role_id, permission_id) [pk]
  }
}

Table customers {
  id uuid [pk]
  business_id uuid [not null]
  name varchar [not null]
  phone varchar [not null]
  email varchar
  address text
  notes text
  created_at timestamptz [default: `now()`, not null]
  updated_at timestamptz [default: `now()`, not null]

  indexes {
    (business_id, phone)
  }

Table categories {
  id uuid [pk]
  business_id uuid [not null]
  name varchar [not null]
  description text
  sort_order integer [default: 0, not null]
  status varchar [default: 'ACTIVE', not null]
  created_at timestamptz [default: `now()`, not null]
  updated_at timestamptz [default: `now()`, not null]
}

Table products {
  id uuid [pk]
  business_id uuid [not null]
  category_id uuid [not null]
  name varchar [not null]
  description text
  image_url text
  price numeric [not null]
  is_available boolean [default: true, not null]
  sort_order integer [default: 0, not null]
  created_at timestamptz [default: `now()`, not null]
  updated_at timestamptz [default: `now()`, not null]
}

Table orders {
  id uuid [pk]
  business_id uuid [not null]
  customer_id uuid

  channel_origin varchar [not null]

  subtotal numeric [default: 0, not null]
  delivery_fee numeric [default: 0, not null]
  total numeric [default: 0, not null]
  notes text
  created_at timestamptz [default: `now()`, not null]
  updated_at timestamptz [default: `now()`, not null]

  indexes {
    (business_id, order_number) [unique]
  }
}

Table order_items {
  id uuid [pk]
  order_id uuid [not null]
  product_id uuid [not null]
  product_name varchar [not null]
  quantity integer [not null]
  unit_price numeric [not null]
  subtotal numeric [not null]
  modifiers_notes text
  created_at timestamptz [default: `now()`, not null]

Table payments {
  id uuid [pk]
  business_id uuid [not null]
  order_id uuid [not null]

  amount numeric [not null]
  payment_method varchar [not null]
  status varchar [default: 'PAID', not null]

Table deliveries {

  phone varchar [not null]
  address text [not null]
  additional_reference text
  delivery_fee numeric [default: 0, not null]
  status varchar [default: 'PENDING', not null]

  updated_at timestamptz [default: `now()`, not null]

  id uuid [pk]
  business_id uuid [not null]
  concept varchar [not null]
  amount numeric [not null]
  category varchar [not null]
  description text

  created_by uuid [not null]
  created_at timestamptz [default: `now()`, not null]

// Catálogo y Clientes
Ref: businesses.id < customers.business_id
Ref: businesses.id < categories.business_id

// Pedidos y Operación
Ref: businesses.id < orders.business_id
Ref: customers.id < orders.customer_id
Ref: orders.id < order_items.order_id
Ref: products.id < order_items.product_id

// Pagos y Domicilios
Ref: businesses.id < payments.business_id
Ref: orders.id < payments.order_id
Ref: orders.id - deliveries.order_id // Relación 1:1 o 1:0..1

// Auditoría y Finanzas
Ref: orders.id < order_status_history.order_id
Ref: users.id < order_status_history.changed_by

Ref: users.id < expenses.created_by
```

# 3. Conjuntos de estados controlados en base de datos

Durante la implementación física en PostgreSQL, estos valores se aplican mediante `CHECK constraints` o `ENUMs`:

- **`businesses.status`:** `'ACTIVE'`, `'INACTIVE'`
- **`users.status`:** `'ACTIVE'`, `'INACTIVE'`
- **`business_users.status`:** `'ACTIVE'`, `'INACTIVE'`
- **`categories.status`:** `'ACTIVE'`, `'INACTIVE'`
- **`orders.channel_origin`:** `'WHATSAPP'`, `'DIGITAL'`, `'IN_PERSON'`
- **`orders.status`:** `'RECEIVED'`, `'PREPARING'`, `'READY'`, `'DELIVERED'`, `'CANCELLED'`
- **`orders.order_type`:** `'PICKUP'`, `'DELIVERY'`
- **`orders.payment_status`:** `'PENDING'`, `'PARCIALLY_PAID'`, `'PAID'`
- **`payments.concept`:** `'PRODUCTS'`, `'DELIVERY'`, `'TOTAL'`
- **`payments.payment_method`:** `'CASH'`, `'TRANSFER'`, `'CARD'`, `'OTHER'`
- **`payments.status`:** `'PENDING'`, `'PAID'`, `'CANCELLED'`
- **`deliveries.status`:** `'PENDING'`, `'IN_PROGRESS'`, `'DELIVERED'`, `'CANCELLED'`
- **`expenses.category`:** `'SUPPLIES'`, `'SERVICES'`, `'PAYROLL'`, `'MAINTENANCE'`, `'OTHER'`

# 4. Reglas no cubiertas por DBML a implementar en Supabase

El código DBML modela la topología de datos; las siguientes reglas de seguridad y lógica se implementan directamente en PostgreSQL:
1. **Row Level Security (RLS):** Aislamiento multi-tenant validando `auth.uid()` contra `business_users`.
2. **Restricciones `CHECK`:** `price >= 0`, `quantity > 0`, `amount > 0`.
3. **Triggers de Auditoría:** Auto-actualización de `updated_at` al modificar registros.
4. **Validación Transaccional:** Disparador para registrar automáticamente en `order_status_history` ante cada UPDATE en `orders.status`.

# 5. Regla de la Fuente de Verdad

Si se requiere modificar una entidad o relación futura, debe seguirse el flujo de cambio en cascada:

$$\text{Requerimiento} \longrightarrow \text{Modelo Conceptual} \longrightarrow \text{Modelo Lógico} \longrightarrow \text{ERD} \longrightarrow \text{Diccionario} \longrightarrow \text{DBML} \longrightarrow \text{SQL Migration}$$

# 6. Alcance y Exclusiones del MVP

Este esquema DBML modela con fidelidad absoluta el alcance del **MVP del Vertical Restaurante de comida rápida**, excluyendo:
- Recetas digitales, mermas o inventario automático por ingredientes.
- Compras a proveedores ni órdenes de compra.
- Facturación electrónica DIAN ni conciliaciones bancarias automáticas.
- Rastreo satelital GPS de repartidores.
