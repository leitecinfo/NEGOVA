## 1. Objetivo

Definir la arquitectura centralizada del sistema de notificaciones de NEGOVA, desacoplando los generadores de eventos de los canales de entrega (**In-App**, **WhatsApp** y **Email**) mediante un bus de eventos asíncrono.

# 2. Catálogo de Eventos Notificables

```text
EVENTO DE DOMINIO           DESTINATARIO    CANAL PRINCIPAL

```

# 3. Canales y Estados de Notificación

```text
                                 EVENTO DE DOMINIO
                                         │
                                         ▼
                             [public.notifications]
                                         │
                   ┌─────────────────────┼─────────────────────┐
                   ▼                     ▼                     ▼
             [ 🔔 IN-APP ]         [ 💬 WHATSAPP ]        [ 📧 EMAIL ]
```

### Estados de la Notificación (`notifications.status`):
- `pending`: En cola para ser despachada.
- `sent`: Entregada exitosamente al proveedor de mensajería.
- `failed`: Error en la entrega externa (sujeto a reintentos).
- `read`: Marcada como leída por el usuario en la interfaz.

# 4. Diagrama del Pipeline de Notificaciones

```mermaid
sequenceDiagram
    autonumber
    participant Domain as Módulo de Pedidos
    participant EventBus as Bus de Eventos
    participant DB as PostgreSQL (notifications)
    participant Worker as Dispatcher en Background
    participant Provider as Proveedor WhatsApp / Email

    Domain->>EventBus: Emitir 'order.ready'
    EventBus->>DB: INSERT INTO notifications (status = 'pending')
    EventBus->>Worker: Notificar nuevo mensaje pendiente
    Worker->>Provider: Enviar mensaje al cliente
    alt Envío Exitoso
        Provider-->>Worker: 200 OK (MessageId)
        Worker->>DB: UPDATE notifications SET status = 'sent'
    else Fallo de Red / Timeout
        Provider-->>Worker: Error 500 / Timeout
        Worker->>DB: UPDATE notifications SET status = 'failed' (programar reintento)
    end
```
