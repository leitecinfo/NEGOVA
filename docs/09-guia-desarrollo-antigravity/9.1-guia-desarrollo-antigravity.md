## 1. Objetivo

Establecer las reglas de ingeniería, estándares de calidad, convenciones de código y la **Definición de Terminado (Definition of Done)** que Antigravity debe seguir de forma estricta e inquebrantable durante toda la construcción del software NEGOVA.

> ⚠️ **Principio Rector:** NEGOVA es un **SaaS Multi-Tenant, Multi-Negocio, Modular y Altamente Seguro**. Jamás debe tratarse ni programarse como una aplicación aislada para un único restaurante.

---

# 2. Stack Tecnológico Oficial

Antigravity solo utilizará las librerías y tecnologías aprobadas:

- **Frontend:** Next.js 14+ (App Router), React 18+, TypeScript 5+, Tailwind CSS 3.4+, shadcn/ui.
- **Backend / Lógica:** Next.js Server Actions y Route Handlers con validación Zod.
- **Base de Datos & Auth:** Supabase (PostgreSQL 15+, Row Level Security, Supabase Auth, Supabase Storage).
- **Facturación SaaS:** Stripe SDK.
- **Despliegue:** Vercel (Edge / Serverless).
- > 🚫 **Queda prohibido introducir frameworks alternativos, ORMs pesados (como Prisma) o servidores Node.js independientes sin autorización.**

---

# 3. Reglas de Arquitectura e Implementación

### 3.1 Flujo Unidireccional de Capas
$$\text{UI (Presentación)} \longrightarrow \text{Server Action (Aplicación)} \longrightarrow \text{Zod (Validación)} \longrightarrow \text{DAL (Supabase)} \longrightarrow \text{PostgreSQL RLS}$$
Ningún componente visual de React debe contener lógica crítica de negocio ni consultas directas SQL.

### 3.2 Scoping Multi-Tenant y Business Context
- Toda entidad operativa (`orders`, `products`, `customers`, `payments`, `expenses`, `files`) debe asociar y filtrar obligatoriamente por `business_id`.
- La aplicación consume y propaga el **Contexto del Negocio Activo** (`Current Business`). El cambio de comercio purga la caché y revalida permisos.

### 3.3 Server Components por Defecto
- Todas las páginas y componentes se crean como **Server Components** por defecto para maximizar la velocidad y seguridad.
- Solo se añade la directiva `'use client'` cuando sea estrictamente indispensable para interacción táctil, formularios reactivos, estados locales (Zustand) o manejo de eventos.

### 3.4 Tipado Estricto (Cero `any`)
- TypeScript configurado con `strict: true`. Queda prohibido el uso de `any` no justificado.

### 3.5 Prohibición de Alertas Nativas
- 🚫 **Prohibido:** `window.alert`, `window.confirm`, `window.prompt`.
- ✅ **Obligatorio:** Modales personalizados (`AlertDialog` de shadcn/ui) para confirmaciones destructivas y notificaciones mediante Toasts (`Sonner`).

# 4. Estados de Interfaz Obligatorios (Los 4 Estados)

Toda vista y componente asíncrono debe implementar de forma obligatoria los cuatro estados de experiencia de usuario:

```text
┌───────────────────────────┬─────────────────────────────────────────────────┐
│ 1. LOADING STATE          │ Skeleton loaders fluidos (cero pantallas vacías)│
├───────────────────────────┼─────────────────────────────────────────────────┤
│ 2. SUCCESS STATE          │ Renderizado reactivo con datos actualizados     │
├───────────────────────────┼─────────────────────────────────────────────────┤
│ 3. ERROR STATE            │ Mensaje amigable al usuario + botón de reintento│
├───────────────────────────┼─────────────────────────────────────────────────┤
│ 4. EMPTY STATE            │ Ilustración/ícono + texto claro + botón de acción│
│                           │ (ej. "Aún no tienes productos" -> [Crear Plato])│
└───────────────────────────┴─────────────────────────────────────────────────┘
```

---

# 5. Orden de Implementación por Dependencias

El desarrollo debe seguir obligatoriamente este orden secuencial:

```text
1. FUNDACIÓN & CONFIGURACIÓN   --> Variables de entorno, Supabase Client, Layout base
2. AUTENTICACIÓN & SESIONES   --> Login, Registro, Recuperación, Middleware JWT
3. CONTEXTO & TENANT SWITCHER --> Carga de membresías, selector de negocio activo
4. USUARIOS & ROLES RBAC      --> Gestión de equipo, matriz de permisos
5. MÓDULOS CORE (CATÁLOGO)    --> Categorías, productos, modificadores, switch disponibilidad
6. MÓDULOS TRANSACCIONALES    --> Comandas, checkout, cola de cocina, estados
7. FINANZAS & PAGOS           --> Recaudos en caja, registro de gastos, balances
8. MÓDULOS OPCIONALES         --> Domicilios, Storage de imágenes, Notificaciones
9. INTEGRACIONES EXTERNAS     --> Webhooks de Stripe, WhatsApp Cloud API
```

# 6. Definición de Terminado (Definition of Done - DoD)

Una funcionalidad **NO está terminada** solo porque "se ve bien en pantalla". Para considerarse completada, debe cumplir el siguiente checklist:

```text
[ ] Sistema de Diseño & Tokens: Cumplimiento estricto del documento 9.2 (tokens de elevación L0-L3, sin clases dark:bg-[#...] arbitrarias).
[ ] Componentes Oficiales: Uso exclusivo de componentes de @/components/ui/ (Button, Input, Select, DataTable, etc.) sin reinventar HTML crudo.
[ ] UI / UX: Diseño limpio, responsivo (Mobile-First) y accesible (anillos de foco visible y contraste WCAG AA).
[ ] Sin Alertas Nativas: Confirmaciones con Modales/ConfirmDialog y feedback con Toasts (Sonner). Cero window.alert.
[ ] Los 4 Estados: Loading (Skeleton), Success, Error (con reintento) y Empty State implementados.
[ ] Validación Zod: Esquema en servidor con tipado TypeScript estricto.
[ ] Seguridad RBAC: Verificación explícita de permisos requeridos en Server Action.
[ ] Aislamiento Multi-Tenant: business_id forzoso y políticas RLS verificadas en Postgres.
[ ] Integridad Referencial: Claves foráneas compuestas aplicadas.
[ ] Manejo de Errores: Interceptor de errores con mensajes sanitizados (cero stack traces).
[ ] Auditoría: Mutaciones sensibles registradas automáticamente en audit_logs.
[ ] Pruebas: Verificación de caso de éxito, caso de error y prueba de acceso cruzado entre tenants.
```

# 7. Los 10 Mandamientos de Antigravity (Regla Maestra)

```text
1.  NO IMPROVISAR ARQUITECTURA.
2.  NO ROMPER EL AISLAMIENTO MULTI-TENANT.
3.  NO CONFIAR EN EL FRONTEND PARA SEGURIDAD (Zero-Trust).
4.  NO USAR ALERTAS NATIVAS (window.alert/confirm).
5.  NO DUPLICAR CÓDIGO VISUAL NI COMPONENTES: Usar siempre el catálogo oficial de 9.2.
6.  NO USAR COLORES HEXADECIMALES ARBITRARIOS: Respetar las 4 capas de elevación del modo oscuro.
7.  NO MODIFICAR LA BASE DE DATOS SIN JUSTIFICACIÓN Y APROBACIÓN.
8.  NO INTRODUCIR LIBRERÍAS O TECNOLOGÍAS INNECESARIAS (No Overengineering).
9.  VALIDAR EL 100% DE LAS ENTRADAS CON ESQUEMAS ZOD EN SERVIDOR.
10. PRIORIZAR SIEMPRE SEGURIDAD, MANTENIBILIDAD, RENDIMIENTO Y EXPERIENCIA DE USUARIO.
```
